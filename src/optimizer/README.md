# Оптимизатор маршрута

Берёт галсы из геометрии и решает, **в каком порядке и в какую сторону**
их пролететь и **как разбить на вылеты** по батарее. Только стандартная
библиотека Python, без shapely/pyproj.

## Запуск

```bash
python -m src.optimizer < request.json          # JSON → JSON, как src.geometry.service
python -m unittest discover -s test              # все тесты, включая геометрию
python test/fixtures/make_fixtures.py            # пересобрать фикстуры (нужен shapely)
```

Из Python: `from src.optimizer import optimize; optimize(payload)`.
Формат запроса и ответа — в docstring `service.py`. На вход в `tracks`
идёт ровно то, что возвращает `FlightPlannerGeometry.process`.
Ошибки — `{"errors": [...]}` и код выхода 1, как у геометрии.

## Как устроено

| Файл         | Что делает                                                                 |
| ------------ | -------------------------------------------------------------------------- |
| `model.py`   | Галс, кодирование «галс + направление» в число, локальная проекция в метры |
| `cost.py`    | Измеритель: покрытие + перелёты + штраф за повороты                        |
| `search.py`  | Змейка, жадный старт, 2-opt/or-opt с переворотом галсов, ILS               |
| `split.py`   | Оптимальное разбиение на вылеты (алгоритм Split)                           |
| `planner.py` | Сборка: порядок → вылеты → доводка каждого вылета                          |
| `service.py` | Граница JSON: разбор, проверки, форматирование ответа                      |

**Модель задачи.** Галс ненаправленный, поэтому единица решения — пара
«галс + направление». Задача — вариант коммивояжёра, где из каждой пары
выбирается ровно один узел, с точкой взлёта и ограничением дальности
вылета.

**Штраф за повороты** пропорционален углу поворота: разворот змейкой
(180°) стоит `turnPenaltyM`, продолжение по прямой — 0. Фиксированный
штраф на переход, как в `geometry/service.py`, от порядка не зависит и
оптимизатору не виден.

**Вылеты.** Сначала строится общий порядок, потом он режется
динамическим программированием — для заданного порядка это точный
оптимум. В лимит вылета входят перелёт к участку, галсы, переходы,
развороты и возврат домой. Без точки взлёта минимизируется число вылетов.

## Результаты на фикстурах

| Участок                   | Галсов | Выигрыш к змейке                            |
| ------------------------- | ------ | ------------------------------------------- |
| Прямоугольник             | 18     | 0 % — на выпуклом участке змейка оптимальна |
| «П» с вырезом             | 37     | ≈ 50 %, с батареей 5 вылетов вместо 10      |
| Вогнутое поле, 167 галсов | 167    | ≈ 35 %, 33 вылета вместо 50                 |

## Встройка в проект

Оптимизатор стоит между нарезкой и распределением по флоту:

```
FlightPlannerGeometry.process  →  src.optimizer  →  plan.segments  →  src.route_optimizer
   галсы «растром»                  порядок и         (фронт)            блоки по БВС
   (строки снизу вверх,             направления
    все слева направо)
```

`plan_mission` в режиме параллельных галсов (`trajectoryAlgorithm: "sweep"`)
отдаёт `plan.segments` уже в порядке облёта. Распределение `contiguous` режет
маршрут на непрерывные блоки **в заданном порядке**, поэтому от порядка
напрямую зависит, сколько БВС понадобится и какой будет налёт. Контурные
проходы, инспекция и коридор не затрагиваются. Если оптимизатор вернул
ошибку, остаётся исходный растровый порядок.

В ответ добавлено поле `plan.routeOrder`: какой порядок применён и насколько
он короче змейки.

Режимы с точкой взлёта и разбиением на вылеты (`depotLonLat`,
`maxFlightDistanceM`) в проекте сейчас не используются: несколько БВС с
домашними площадками обслуживает `src.route_optimizer`. Они остаются в
модуле как библиотека и покрыты тестами.

## Известные ограничения

- Перелёты — по прямой: запретных зон в проекте пока нет.
- Один борт. Несколько дронов — следующий шаг (та же модель, split по бортам).
- Время = дистанция / скорость, без разгона и набора высоты.
